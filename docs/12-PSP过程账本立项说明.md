# PSP 过程账本：课内工程过程轻量化助手立项说明

> 文档用途：软件项目立项论证、需求边界澄清、技术方案备忘。  
> 项目定位：把实验课要求的五类 PSP 文档，从 Word / 手工填表，升级为「过程数据采集 → 自动草稿 → 人工确认 → 合规导出」。

---

## 1. 项目概述

### 1.1 一句话定义

**PSP 过程账本**：面向软件工程实验课的个人 / 小组过程数据助手。学生用半自动方式记录开发活动，系统生成五类 PSP 表单草稿，经人工确认与规则校验后，一键导出可提交包。

### 1.2 要解决的核心问题

| 现状 | 后果 |
| --- | --- |
| 时间靠事后回忆补记 | 漏记、记不准、可信度低 |
| 五类表分散在多个 Word / 表格 | 周整理耗时长、字段不一致 |
| 命名与归档靠人工记忆 | 格式被退回、反复返工 |
| 过程与 Git / 作业编号脱节 | 计划与实际难对照、答辩难举证 |

### 1.3 产品闭环

```text
日常开发痕迹（手工记时 / Git / 可选 CLI）
        ↓
系统生成「表单草稿」
        ↓
学生人工确认、改错、补备注
        ↓
按课内命名与归档规则校验
        ↓
一键导出「可交」提交包（zip / 指定格式）
```

**关键原则**：系统不替代填写责任，只降低补记成本与格式错误；导出前必须有人工确认闸门。

## 2. 项目背景与痛点数据口径

### 2.1 课内硬约束（可直接引用）

- 交付物固定为五类 PSP 文档：工程记事本、时间记录日志、周活动总结表、作业编号日志、项目计划总结表
- 使用周期跨实验课中后期（约周 3–17），属于持续过程，而非一次性作业
- 存在编号、命名、归档规范；提交常要求可在线预览的指定格式

### 2.2 建议补充的本班问卷（30–50 人即可）

1. 上周整理 / 补记 PSP 大概花了多久？（`<15` / `15–30` / `30–60` / `>60` 分钟）
2. 是否出现过「事后补记、记不准」？
3. 是否因命名 / 格式被退回或返工？
4. 最耗时的是哪一类表？

### 2.3 成功标准（时间 + 范围 + 量化指标）

- **时间**：试点用户周整理时长中位数从约 45 分钟降至 `≤10` 分钟
- **范围**：覆盖五类表单草稿 + 命名 / 必填校验 + 导出提交包
- **指标**：漏记相关返工下降 `≥50%`；命名 / 归档一次通过率 `≥90%`（以校验器或抽查为准）

## 3. 目标用户与使用场景

### 3.1 用户

- **主用户**：需持续提交 PSP 的学生（个人）
- **协同用户**：小组长（查看成员是否按时汇总）
- **次用户**：助教（抽查格式；系统不做自动评分）

### 3.2 典型场景

1. 工作日：结束一段编码后，补一条时间记录（活动类型、作业编号、备注）
2. 周五：一键生成「周活动总结表」草稿，核对计划 vs 实际
3. 提交前：跑命名与必填校验，导出合规 zip
4. 里程碑：更新「项目计划总结表」，关联关键 commit / 分支

### 3.3 明确不做

- 不替代教师评分
- 不支持无人工确认的全自动提交
- 第一期不做深度 IDE 键鼠监控
- 不做多学校 SaaS、复杂企业权限与审批流
- 不爬取、不对接对分易账号自动交作业

## 4. 需求分析

### 4.1 功能需求（MoSCoW）

| 优先级 | 功能 | 说明 |
| --- | --- | --- |
| Must | 账号与身份 | 学号 / 姓名；数据按人隔离 |
| Must | 五类表单结构化编辑 | 字段可映射到课内空白表，不要求像素级复刻 Word |
| Must | 时间记录 | 手工 / 半自动条目：起止时间、活动类型、作业编号、备注 |
| Must | 规则校验 | 命名、必填、编号连续性等；导出前给出错误列表 |
| Must | 合规导出 | 生成指定格式提交包；导出前强制「我已核对」确认 |
| Should | Git 关联 | commit / 分支 / PR 关联到作业编号 |
| Should | 周活动汇总 | 从时间日志自动聚合到周表草稿 |
| Should | 未填提醒 | 本周缺哪张表、哪类活动时长为 0 |
| Should | 导出快照 | 每次导出保留版本，便于返工对比 |
| Could | 本地 CLI 打点 | 如 `psp punch in/out`，减少回想 |
| Could | IDE 插件估时 | 隐私争议大，适合作为会议决策议题 |
| Could | 小组看板 | 成员按时率、滞后提醒 |
| Could | 说明核对清单 | 对照作业说明逐项勾选 |
| Won't | 自动评分 | — |
| Won't | 无人确认直交 | — |
| Won't | 全盘键鼠 / 屏幕监控 | — |

### 4.2 非功能需求

- **性能**：单次表单保存 `<1s`；百级条目导出 `<5s`
- **安全**：仅本人（及授权组员）可见；导出包不含他人数据
- **隐私**：默认半自动采集；任何自动采集必须可关闭
- **可用性**：桌面端完整编辑；移动端至少能补记一条时间
- **可维护**：命名正则、必填项、模板路径配置化，避免写死在代码中

### 4.3 需求优先级决策依据

1. 没有「校验 + 导出」就无法解决退回问题 → Must
2. Git 关联能提升可信度，但手工记时也能闭环 → Should
3. IDE 插件收益高、争议与实现成本也高 → Could / 会议拍板

## 5. 可行性论证

### 5.1 技术可行性

- Web 表单 + 规则引擎 + 模板导出，技术栈成熟，一学期可交付 MVP
- Git 集成可用「粘贴 commit」或 webhook 半自动，不必先做 IDE 插件
- 主要技术风险是「必须与 Word 排版完全一致」——用字段映射 + 模板导出规避，在立项书中写清验收口径

### 5.2 经济可行性（课程口径）

- **成本**：4–6 人一学期人力 + 小规格云主机或本地 Docker
- **收益**：人均每周节省整理时间 × 人数 × 周数；降低退回返工
- **示例**：人均每周省 30 分钟，40 人 × 15 周 ≈ 300 人时
- **回收期**：教学场景写「效率回收」即可，不强制商业回本叙事

### 5.3 运营 / 组织可行性

- 推广路径：本组先用 → 班级试点 → 助教按导出包抽查格式
- 习惯阻力：Must 保证纯手工可用，自动能力只是加速器
- 责任边界：系统保证格式与完整性提示；内容真实性由学生确认

### 5.4 法律 / 合规可行性

- 最小化采集：优先手工与用户授权的 Git 数据
- 学号等个人信息最小必要、可导出可删除
- AI 仅生成草稿，须标注「AI 辅助 + 人工修改」
- 不涉及支付、不爬取第三方教学平台

## 6. 技术方案

### 6.1 逻辑架构

```text
[Web 端 / 可选 CLI]
        ↓
[应用层] 表单服务 · 汇总服务 · 校验服务 · 导出服务
        ↓
[领域层] 时间条目 · 作业编号 · 周汇总 · 计划基线 · 导出快照
        ↓
[基础设施] 数据库 · 模板引擎 · Git 适配器 ·（可选）对象存储
```

### 6.2 关键数据流

1. 用户记录：`14:00–16:30`，活动=编码，作业编号=`E1`
2. 周末执行「生成周草稿」：周活动表写入计划 / 实际小时
3. 校验：缺本周工程记事本条目 → 阻断导出并列出错误
4. 用户确认 → 导出如 `学号_周次_PSP.zip`

### 6.3 技术选型原则（约束 → 选择）

| 约束 | 选择建议 |
| --- | --- |
| 一学期、4–6 人、要可演示 | 选用组内最熟的后端（如 Java / Spring）与前端栈 |
| 课规会微调 | 规则与模板外置（YAML / JSON + 模板文件） |
| 隐私敏感 | 默认手工 / 半自动；插件级采集放 Could |
| 提交格式固定 | 模板导出优先于自由富文本 |

### 6.4 部署形态

- 推荐：单体后端 + 前端静态资源 + MySQL / PostgreSQL
- 可用 Docker Compose 本地 / 小主机一键启动，便于课堂演示

## 7. 范围、WBS、进度、成本与风险

### 7.1 范围

- **MVP**：Must 全部完成
- **增强**：Should 选做 2–3 项
- **演示彩蛋**：Could 任选其一做 PoC 即可

### 7.2 WBS（工作分解）

1. 课规规则提取（字段字典、命名正则、必填矩阵）
2. 账号与基础权限
3. 五类表单 CRUD
4. 时间日志与周汇总
5. 校验引擎
6. 导出与快照
7. Git 半自动关联（Should）
8. 测试、试点、文档与演示素材

### 7.3 进度粗排（一学期）

| 阶段 | 周次（相对） | 产出 |
| --- | --- | --- |
| 规则与原型 | 第 1–2 周 | 字段字典、可点击原型 |
| MVP 实现 | 第 3–6 周 | 表单 + 校验 + 导出 |
| 增强与硬化 | 第 7–10 周 | 汇总、提醒、Git 关联 |
| 试点与收尾 | 第 11–14 周 | 试点数据、缺陷修复、演示 |

预留缓冲给「导出格式口径变更」。

### 7.4 成本构成

- 人力：后端、前端、测试 / 文档、组长
- 资源：云主机小规格或实验室机器
- 风险预算：预留约 15%–20% 人周应对规则变更

### 7.5 风险清单

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 课规 / 导出格式变更 | 高 | 规则与模板配置化 |
| 自动采集引发隐私争议 | 中 | 默认半自动；采集做开关 |
| 要求与 Word 像素级一致 | 高 | 立项写清：字段完备 + 可预览，不承诺排版一致 |
| 推广冷启动 | 中 | 先服务本组 PSP，再扩班级 |
| AI 幻觉写入过程数据 | 中 | AI 只出草稿；导出强制人工确认 |

## 8. AI 使用说明（课设合规）

### 8.1 适合 AI 的部分

- 从课规文档抽取字段清单、生成校验规则初稿
- 周报文字润色、记事本条目扩写（必须人工改定）
- 立项书润色、演示视频脚本与分镜

### 8.2 必须由人完成的部分

- Must / Won't 与隐私边界决策
- 每条时间记录的真实性确认
- 校验规则与任课口径对齐
- 导出格式验收

**表述建议**：AI 提升文档与草稿效率；真实性与合规由人工闸门保证。

## 10. 验收标准

1. 能完整走通：记时 → 五类表可编辑 → 校验 → 导出
2. 故意构造至少 3 类错误（缺字段、错文件名、缺周汇总）可被检出
3. 至少一个小组连续使用 `≥3` 周，并有整理耗时前后对比
4. 交付文档含：AI 使用说明、范围说明、部署说明

## 11. 总结：有价值的业务点

以下从「课设外壳」抽离，归纳本项目真正值得做、也值得对外讲的业务价值。课设答辩强调前半；实习 / 作品集叙事强调后半的可迁移能力。

### 11.1 直接业务价值（对本课用户）

1. **降低过程合规成本**  
   把「记得填、填得对、导得出」做成产品能力，减少每周补记与退回返工。

2. **提升过程数据可信度**  
   时间条目可关联作业编号与 Git 痕迹，计划 vs 实际可对照，答辩与抽查有据可查。

3. **用规则引擎替代口头规范**  
   命名、必填、编号连续性从前置说明变成可执行校验，一次通过率可量化。

4. **保留人责边界，避免「假自动化」**  
   人工确认闸门明确「系统辅助、人对内容负责」，既符合教学要求，也符合真实业务里的合规习惯。

5. **小范围可运营**  
   个人可用、小组可汇总、助教可抽查格式；不依赖支付、物流等重运营模块即可闭环。

### 11.2 可迁移的业务能力（对实习 / 工程叙事更有价值）

1. **过程数据采集与结构化**  
   把散落在聊天、记忆、仓库里的活动，沉淀为可查询、可汇总的结构化事件流——接近工时、审计、研发效能类产品的核心模型。

2. **合规导出 / 交付打包**  
   「校验 → 确认 → 按模板出包」是报告交付、监管报送、客户验收包的通用模式，不绑定 PSP。

3. **半自动优于全自动的产品策略**  
   在隐私敏感场景用「用户授权 + 人工确认」换取可落地性，体现需求权衡能力，而非堆监控功能。

4. **配置化规则与模板**  
   业务规则外置，能应对口径变更；这是 ToB / 教务 / 企业内部工具最常见的生存技能。

5. **可度量的成功标准**  
   用时长、一次通过率、返工率定义验收，避免「功能做了但说不清价值」——面试时这是加分叙事。

6. **范围砍削与分期交付**  
   Must / Should / Could / Won't 清晰，说明能在资源约束下保主路径，这是项目制实习最看重的协作素质之一。

### 11.3 一句话收束

**课内卖点**：让 PSP 从「痛苦补表」变成「草稿确认 + 合规导出」。  
**对外卖点**：一套「过程事件 → 规则校验 → 人工确认 → 模板交付」的轻量合规流水线，可映射到工时台账、变更检查清单、验收打包等真实业务。

若实习作品集使用本项目，建议对外命名为「个人 / 团队工程过程台账与合规导出系统」，弱化课表术语，强化本节 11.2 的六项能力。
