### 2.1 HTTP 与鉴权

**一句话**：用预签名 URL 让客户端直传对象存储，用 HMAC-SHA256 给播放 URL 签名防盗链，两者都不把密钥交给前端。

#### 原理

**预签名 URL（Presigned URL）**

对象存储的 AccessKey / SecretKey 不能给前端。服务端用 SecretKey 对「方法 + 桶 + 对象 + 过期时间」签名，生成一个带签名的 URL，前端拿这个 URL 在过期前可直接 `PUT` / `GET` 对象，不需要经过业务机。

- 优点：大文件不经业务机，省带宽、易扩展。
- 关键参数：`method`、`bucket`、`object`、`expires`。
- 安全模型：签名只对这一次操作有效，过期作废；SecretKey 始终在服务端。

**HMAC-SHA256**

\[ \text{sign} = \text{Hex}\big(\text{HMAC}_{\text{SHA256}}(\text{secret}, \text{payload})\big) \]

- HMAC = Hash-based Message Authentication Code，用密钥给消息算摘要。
- 比「明文拼接 secret 再 hash」安全：HMAC 的构造避免了长度扩展攻击。
- 验签时重算签名，用**恒等时间比较**（`MessageDigest.isEqual`）防时序攻击。

**签名 URL vs JWT**

| 维度 | 签名 URL | JWT |
| --- | --- | --- |
| 载体 | URL query | Header `Authorization: Bearer` |
| 内容 | 通常无 payload，只签名 | 自带 payload（claims） |
| 校验 | 服务端重算签名 | 服务端验签 + 读 claims |
| 适用 | 单个资源、有过期 | 用户身份、会话 |
| 撤销 | 难（靠短 TTL） | 难（靠短 TTL 或黑名单） |

本项目播放用签名 URL：资源绑定 path，过期靠 `e`，试看靠 `exper`，不需要用户身份，所以不引入 JWT。

### 2.2 对象存储 S3

**一句话**：S3 用「桶 + 对象键」存文件，预签名让前端直传，`HEAD` 确认存在，大文件不经业务机。

#### 原理

- **Bucket（桶）**：顶层命名空间，名字全局唯一。本项目桶名 `vod`。
- **ObjectKey（对象键）**：桶内唯一标识，形如 `raw/{fileId}/source.mp4`。注意它**不是文件路径**，但用 `/` 分层便于前缀删除。
- **操作**：`PUT` 上传、`GET` 下载、`HEAD` 只取元数据（存在性、大小、Content-Type）、`DELETE` 删除。
- **预签名**：见 2.1。
- **为何不经业务机传大文件**：业务机带宽是瓶颈，且占 CPU / 内存；直传让对象存储扛流量，业务机只做元数据与调度。

**MinIO 与 S3 的关系**：MinIO 实现 S3 协议，SDK 与 API 兼容；本地用 MinIO，上云可换腾讯云 COS / 阿里云 OSS，业务代码几乎不动。

#### 本项目怎么做

### 2.3 异步与 MQ

**一句话**：转码是 CPU 密集任务，放 MQ 后由 Worker 异步消费，靠状态机 + 幂等 + 重试保证最终一致。

#### 原理

**为何不能同步**

- 转码 720p HLS 可能几十秒到几分钟，HTTP 同步会超时、占线程、阻塞 API。
- 把任务丢 MQ，API 立刻返回 `PROCESSING`，Worker 慢慢转，转完回写库。

**幂等**

- 重复 commit 同一 `fileId` 不应重复建任务、重复转码。
- 本项目靠「查未完结任务」做幂等：已有 `PENDING` / `RUNNING` 就直接返回。

**重试与死信**

- 失败重试有限次（`maxAttempts`），超过则 ack 停止，避免毒消息把队列打爆。
- 重试靠 `basicReject(deliveryTag, true)` requeue，让 MQ 重投。
- 死信队列（DLQ）是更规范的做法：超过次数转 DLQ 人工处理。本项目首期用「ack 停止 + Webhook FAILED」简化。

**at-least-once**

- MQ 不保证 exactly-once，消费端可能收到重复消息。
- 所以消费逻辑必须幂等：靠任务状态 + `attempt` 计数。

**两个状态机**

媒资状态：

```8:19:lite-vod/vod-common/src/main/java/com/example/vod/common/domain/media/MediaStatus.java
 *   <li>UPLOADING(0) - 上传中</li>

 *   <li>FINISHED(3) - 已完成</li>
 *   <li>FAILED(4) - 失败</li>
```

为什么要分两张表：一个媒资可能多次转码（重转、改码率），任务行记每次尝试；媒资行只存当前最新状态。

### 2.4 视频与 HLS

**一句话**：HLS 把视频切成一堆 `.ts` 小片加一个 `index.m3u8` 清单，网页用 hls.js 按清单顺序拉，比直接播 mp4 友好且可切片鉴权。

#### 原理

**容器 vs 编码**

- **容器**（封装格式）：`mp4`、`flv`、`ts`、`mkv`，决定怎么把音视频流装在一起。
- **编码**（压缩算法）：`H.264` / `H.265`（视频）、`AAC` / `MP3`（音频），决定怎么压缩像素和声音。
- 一个 `mp4` 文件里可以是 `H.264 + AAC`，也可以是 `H.265 + AAC`；容器和编码是两层。

**HLS 结构**

```text
index.m3u8          # 清单：列出每个 ts 的文件名和时长
├── segment_000.ts  # 切片，通常 6～10 秒
├── segment_001.ts
└── ...
```

`m3u8` 是文本清单，形如：

```
#EXTM3U
#EXT-X-TARGETDURATION:6
#EXTINF:6.0,
segment_000.ts
#EXTINF:6.0,
segment_001.ts
#EXT-X-ENDLIST
```

**为何网页少直接播原片 mp4**

- 原片可能很大，浏览器要等下载才能拖进度（除非服务器支持 Range）。
- HLS 切片小，可边下边播、弱网自适应、CDN 缓存友好。
- 切片可单独鉴权（本项目把签名透传到每个 `.ts`）。
- 转码后统一 `H.264 + AAC`，兼容性比五花八门的原片好。

**点播 vs 直播**

- 点播：清单末尾有 `#EXT-X-ENDLIST`，切片固定。
- 直播：清单不断刷新，新切片追加，无 `ENDLIST`。

### 2.5 FFmpeg / ffprobe

**一句话**：FFmpeg 把原片转 HLS + 截封面，ffprobe 读时长；进程调用要设超时、读 stderr、失败截断写 `error_msg`。

#### 原理

**三条核心命令**

1. **转 HLS**：`ffmpeg -i source.mp4 -vf scale=-2:720 -c:v libx264 ... -f hls index.m3u8`
2. **截封面**：`ffmpeg -ss 00:00:03 -i source.mp4 -vframes 1 cover.jpg`
3. **读时长**：`ffprobe -show_entries format=duration -of default=noprint_wrappers=1:nokey=1 source.mp4`

**关键参数**

- `-y`：覆盖输出，避免交互卡住。
- `-ss` 放 `-i` 前：seek 快（按关键帧），放后面是精确但慢。
- `-preset`：编码速度档，`medium` 是默认；`fast` 更快但文件更大。
- `-hls_time 6`：每片约 6 秒。
- `-hls_list_size 0`：清单包含全部切片（0 = 不限），点播必须。

**进程调用要点（Java ProcessBuilder）**

- 必须设超时，否则 FFmpeg 卡住会拖死 Worker。
- 必须读 stdout / stderr，否则缓冲区满会死锁。
- 退出码非 0 视为失败，把 stderr 截断写 `error_msg`。
- 失败要清理临时目录，避免磁盘泄漏。

**为何片长短于 3 秒要用 0 秒截封面**：`-ss 00:00:03` 在 2 秒的视频上取不到帧，会失败；所以短片改用 `00:00:00`。

### 2.6 后端通用

**一句话**：MySQL 靠索引与事务保一致，线程池控并发，异常与超时防雪崩；这些都是面试必考基础。

#### 原理

**MySQL 索引与事务**

- **唯一索引**：`media.file_id` 加唯一索引，防止重复插入；commit 幂等的最后一道闸。
- **事务**：`@Transactional` 包住「建任务 + 改状态 + 发 MQ」，任一失败回滚。
- **隔离级别**：默认 `REPEATABLE READ`（MySQL InnoDB），多数业务够用。
- **行锁**：`UPDATE ... WHERE id = ?` 走索引会加行锁，避免并发改同一行。

**线程池**

- 核心参数：核心线程数、最大线程数、队列容量、拒绝策略。
- 转码是 CPU 密集，线程数 ≈ CPU 核数；IO 密集可大一些。
- 本项目 Webhook 回调用异步线程池，不阻塞主流程。

**异常与超时**

- HTTP 调用必须设超时（connect + read），否则下游慢会拖垮上游。
- 异常分类：业务异常（4xx，可重试或提示）vs 系统异常（5xx，告警）。
- Spring 用 `ResponseStatusException` 把异常映射到 HTTP 状态码。

**幂等键**

- 接口幂等靠「业务唯一键 + 查已存在」或「token 表」。
- 本项目 commit 靠 `file_id` 唯一 + 查未完结任务。

### 2.7 CI/CD

**一句话**：MR 触发单测做质量门禁，`main` 构建镜像推 Harbor，手动 `deploy_staging` 拉镜像到演示机，按 tag 回滚。

#### 原理

**CI（持续集成）**

- 代码 push / MR 自动跑测试和构建，失败阻断合入。
- 作用：尽早发现问题，避免「我本地能跑」。
- 关键：质量门禁（Pipelines must succeed）、分支保护（`main` 禁直推）。

**CD（持续部署 / 交付）**

- 部署分自动和手动：演示机可手动触发，生产建议人工确认。
- 本项目 `deploy_staging` 是手动 Job，点一下才部署。

**Harbor 的角色**

- 私有镜像仓库，存构建好的 Docker 镜像。
- 镜像 tag 用 commit 短哈希（`$CI_COMMIT_SHORT_SHA`），可追溯、可回滚。
- 演示机 `docker login` Harbor 后 `compose pull` 拉镜像。

**CI Variables**

- 密钥不入仓库：Harbor 账号、SSH 私钥、`VOD_PLAY_SECRET` 都走 GitLab Variables。
- File 类型变量（如 SSH 私钥）保留换行，普通变量会吃掉换行导致 SSH 报错。

**回滚**

- 按镜像 tag 回滚：把 `.env` 里 `IMAGE_TAG` 改成旧 sha，重新 `compose pull && up -d`。
- 因为 tag = commit，能精确回到任意一次构建。

**链路**

```text
git push main
  → test（Maven 单测）
  → build_push（打包并推 vod-api、vod-worker 到 Harbor）
  → deploy_staging（手动：SSH 到目标机，compose pull && up，再查健康检查）
```

### 3.2 CDN、Range、缓存

**一句话**：CDN 把切片缓存到边缘，播放器用 Range 请求某段字节，拖进度靠这两者加速。

#### 原理

- **CDN**：内容分发网络，边缘节点缓存 `.ts`，用户就近拉，降低源站压力。
- **Range 请求**：`Range: bytes=0-1023`，HTTP 支持只取部分字节，断点续传和拖进度用。
- **缓存**：`Cache-Control: max-age`，切片不变可长缓存；清单短缓存（直播要刷新）。
- **回源**：CDN 没命中时回源站（MinIO）拉，命中则直接返回。

#### 本项目现状

网关设了 `Cache-Control: private, max-age=60`，演示用单机没 CDN。生产建议切片长缓存、清单短缓存，CDN 回源到 MinIO 或网关。

### 3.5 直播 vs 点播、RTC 皮毛

**一句话**：点播是固定文件切片，直播是不断刷新清单，RTC 是端到端低延迟实时通信，三者协议和延迟不同。

#### 原理

| 类型 | 协议 | 延迟 | 切片 |
| --- | --- | --- | --- |
| 点播 | HLS | 秒级 | 固定，有 `ENDLIST` |
| 直播 | HLS / FLV / RTMP | 几秒～十几秒 | 不断刷新追加 |
| RTC | WebRTC / RTP | 毫秒级 | 无切片，实时流 |

- 直播清单无 `#EXT-X-ENDLIST`，播放器轮询拉新切片。
- RTC 走 UDP + SRTP，延迟低但实现复杂，常配合 STUN/TURN 打洞。

#### 本项目现状

只做点播。了解概念即可拓宽岗位面（声网 / 云信向）。

## 五、面试叙事串联

把知识点串成一个故事，约 5～8 分钟：

1. **上传**：客户端先申请预签名 URL（不把 SecretKey 给前端），直传 MinIO，再 `commit` 让服务端 `HEAD` 确认存在、校验大小、落库为 `UPLOADING`。
2. **转码**：commit 在事务里建 `media_task`、改 `PROCESSING`、发 RabbitMQ；Worker 消费用 FFmpeg 转 720p HLS + 截封面，回传 MinIO，写 `FINISHED`。失败有限重试，超过 ack 停止防毒消息。
3. **播放**：客户端拿 `fileId` 换播放签名 URL（HMAC-SHA256，带 `e` 过期、`exper` 试看）；网关验签后流式回写，并把签名透传到 `m3u8` 里每个 `.ts`。
4. **防盗链**：无签名、过期、篡改 path 都 403；恒等时间比较防时序攻击。
5. **工程化**：GitLab CI 跑单测做门禁，`main` 构建推 Harbor（tag = 短哈希），手动 `deploy_staging` 拉镜像到演示机，按 tag 回滚。

讲完这五段，面试官追问的细节都能在本文对应小节找到答案。
