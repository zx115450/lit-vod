> 分期：Phase 1（部分进入 Phase 2 的衔接）。  
> 目标：实现 `POST /vod/medias`：校验对象存在，更新为 `UPLOADED`。本步 **先不发 MQ**（发队列在第 08 步）。  
> 上一篇：[申请上传凭证](./05-申请上传凭证.md)　下一篇：[媒资查询](./07-媒资查询.md)

## 本步要做什么

对应天机学堂 `saveMedia`：前端直传完成后告诉服务端「文件已在桶里」，服务端 HeadObject 后落元数据。

实现文档要求 commit 后立刻建任务并 `PROCESSING`。为降低联调难度，本步可先停在 `UPLOADED`；第 08 步再补「建任务 + 投递 + PROCESSING」。若你希望一次写完，读完第 08 步后把两处逻辑写在同一个 Service 方法里即可，但验收时仍建议分两次测。

## 接口契约

- **方法 / 路径**：`POST /vod/medias`
- **请求体**：

```json
{
  "fileId": "f7c2a1b0e9d84f6a",
  "filename": "lesson01.mp4"
}
```

- **成功**：返回当前 `MediaDTO`（fileId、filename、status、size 等）
- **对象不存在**：4xx，不更新状态（测试 T3）

## 处理流程（本步范围）

1. 按 `fileId` 查 `media`，不存在则 404
2. HeadObject(`object_key`)；失败则 4xx，文案明确「未找到上传对象」
3. 写入 `filename`、`size`（来自 Head）
4. `status = UPLOADED(1)`
5. 返回 DTO

幂等（实现文档）：若已是 `PROCESSED`，直接返回，不重复建任务。本步至少做到：重复 commit 已 `UPLOADED` 的记录可更新 filename 或直接返回，不要插第二条 `media`。

## 操作步骤

### 1. 实现 `MediaService.commit(fileId, filename)`

把 MinIO `head` / `stat` 与数据库更新放在同一方法。Head 失败不要把状态改成 FAILED（用户可能稍后重传）。

### 2. 限制（可本步先做校验，真正 FAILED 在 Worker）

- 单文件大小上限（如 2 GB）：超限 4xx
- 时长限制在转码探测后做（第 09 步）

### 3. 验证

1. 调上传凭证
2. PUT 文件到 MinIO
3. `POST /vod/medias`
4. 查库 `status=1`，`size > 0`，`filename` 正确

反向：不上传直接 commit，应 4xx。

## 完成标准

- [ ] 合法直传后 commit 成功，`UPLOADED`
- [ ] 未上传 commit 失败
- [ ] 同一 `fileId` 不会插入第二行 `media`
