# 密码学：开发实用指南

> 面向业务开发：讲清「用什么、为什么、常见坑」，不展开证明。  
> 与本仓库相关：播放 URL 的 [HMAC-SHA256 签发](./05-分步实现指南/10-播放签名签发.md) / [网关验签](./05-分步实现指南/11-播放网关验签.md)。

---

## 1. 先分清几类能力

开发里常把「加密」「签名」「哈希」混着说，实际职责不同：

| 能力 | 典型问题 | 常见算法 | 密钥特点 |
| --- | --- | --- | --- |
| **哈希（Hash）** | 内容有没有变？能否当指纹？ | SHA-256、SHA-3、BLAKE2 | 无密钥 |
| **消息认证（MAC）** | 内容有没有被改？是不是持密钥方发的？ | HMAC-SHA256 | **同一把** secret |
| **数字签名** | 谁签的？能否用公钥验？ | RSA-PSS、ECDSA、Ed25519 | 私钥签 / 公钥验 |
| **对称加密** | 别人能不能看懂密文？ | AES-GCM、ChaCha20-Poly1305 | 同一把密钥加解密 |
| **非对称加密** | 只用公钥就能加密？ | RSA-OAEP、ECIES（少见直用） | 公钥加密 / 私钥解密 |
| **密钥交换** | 如何安全协商会话密钥？ | ECDH、X25519 | 双方临时密钥 |

口语里的「签名 URL」在本项目里是 **HMAC（MAC）**，不是 RSA/ECDSA 那种数字签名。

---

## 2. 哈希：指纹，不是加密

### 2.1 做什么

对任意长度输入算固定长度摘要。相同输入 → 相同输出；改一点点 → 输出大变。

常见用途：

- 文件 / 内容完整性校验（如对象 ETag、软件包校验）
- 密码存储的**前置步骤**（还要加盐、用专门的密码哈希，见下文）
- 构造 HMAC、数字签名的内部步骤

### 2.2 开发注意

- **不可逆**：从哈希推不回原文（在正确算法下）
- **不是加密**：哈希结果常可公开；加密密文需要密钥才能恢复明文
- **别用 MD5 / SHA-1 做安全用途**：碰撞攻击已现实可用；完整性场景也尽量换 SHA-256
- **密码不要只做一次 SHA-256**：应使用 `bcrypt` / `scrypt` / `Argon2` 等慢哈希

本项目 `PlaySignService` 里 `MessageDigest.isEqual` 是用来**比较两个字符串/字节是否相等**，不是在做内容哈希。

---

## 3. HMAC：开发里最常用的「签名」

### 3.1 是什么

**HMAC** = 用密钥控制的哈希。公式概念上是：

$$
\text{HMAC}(K, m) = H\bigl((K' \oplus \text{opad}) \,\|\, H((K' \oplus \text{ipad}) \,\|\, m)\bigr)
$$

开发只需记住：

```text
tag = HMAC_SHA256(secret, message)
```

- `secret`：双方共享，不能泄露
- `message`：待保护的字节串（常由业务字段按固定规则拼接）
- `tag`：认证码（再常转成 hex / Base64 放进 URL 或 Header）

### 3.2 适合什么场景

- CDN / 播放 **签名 URL**（本项目）
- Webhook 验真（如支付回调、GitHub webhook）
- API 请求签名（部分开放平台）
- 会话 Cookie 防篡改（部分实现）

### 3.3 本项目怎么用

待签名字符串（实现文档 8.1）：

```text
path={uriPath}&e={expireEpoch}&exper={experSeconds|0}
```

签发：

```text
sign = Hex(HMAC_SHA256(secret, 待签名字符串))
```

代码路径：`lite-vod/vod-api/.../PlaySignService.java`

1. `buildPayload` 拼明文
2. `hmac` 用 `Mac.getInstance("HmacSHA256")` + `SecretKeySpec`
3. `hex` 转成小写十六进制
4. `verify` 重算后用 `MessageDigest.isEqual` 比较（防时序攻击）

约定必须双方一致：

- 同一 `secret`
- 同一拼接顺序与字段含义
- 同一字符编码（UTF-8）
- 同一 hex 大小写（本项目统一小写）
- 同一过期语义（`now >= e` 视为失效）

### 3.4 常见坑

| 坑 | 说明 |
| --- | --- |
| 拼接规则漂移 | `path` 带不带 query、`exper` 负数怎么处理，必须写死 |
| 编码不一致 | Java `getBytes()` 不写 `UTF_8` 会跟环境有关 |
| 用 `==` / `equals` 比签名 | 短时失败路径可能泄露信息；用恒等比较 |
| secret 进仓库 / 日志 | 环境变量注入，勿提交、勿打印 |
| 把 HMAC 当加密 | 攻击者看不到明文以外的东西，但 HMAC **不保密** 明文 |

## 4. 对称加密：保密传输 / 落盘

### 4.1 推荐形态

优先选 **AEAD**（带认证的加密），同时提供保密 + 防篡改：

- **AES-GCM**
- **ChaCha20-Poly1305**

避免自己拼：`AES/ECB`、裸 `AES/CBC` 再手搓 HMAC（容易漏 nonce、漏认证）。

### 4.2 必须管好的三样

1. **密钥**：足够随机，长度符合算法（AES-128/256）
2. **Nonce / IV**：几乎每次加密都要唯一；GCM 下重复 nonce 会灾难
3. **关联数据 AAD**（可选）：把「不加密但要防改」的字段（如用户 ID、版本号）绑进认证

密文通常打包：`nonce || ciphertext || tag`（或库规定的封装格式）。

### 4.3 和 HMAC 怎么选

| 需求 | 选型 |
| --- | --- |
| 只防篡改、明文可暴露（签名 URL） | HMAC 足够 |
| 明文不能暴露 | 对称加密（AEAD） |
| 既要保密又要证明来源（跨信任域） | TLS + 应用层签名，或数字签名 |

播放签名 URL 里的 `path`、`e`、`exper` 本来就要给播放器看，所以用 HMAC 而不是 AES。

## 5. 非对称：TLS、JWT、证书里的「真签名」

### 5.1 数字签名 vs HMAC

| | HMAC | 数字签名（如 ECDSA） |
| --- | --- | --- |
| 密钥 | 共享 secret | 私钥 / 公钥对 |
| 谁能验 | 持有 secret 的所有人 | 任何人（有公钥即可） |
| 谁能签 | 持有 secret 的所有人 | 仅私钥持有者 |
| 典型 | 签名 URL、Webhook | JWT（非对称）、代码签名、HTTPS 证书 |

网关和签发服务若**都持有同一 `VOD_PLAY_SECRET`**，用 HMAC 简单高效。若「很多客户端要验、但不能会签」，才考虑非对称。

### 5.2 开发里常碰到

- **HTTPS / TLS**：浏览器与服务器之间的保密与身份，底层大量非对称 + 对称会话密钥
- **JWT**：
  - `HS256`：本质是 HMAC，和共享密钥同一类
  - `RS256` / `ES256`：真·数字签名
- **对象存储预签名 URL**：常由云厂商 SDK 用访问密钥算签名（概念上类似 HMAC 家族，细节跟厂商）

本项目 MinIO 上传凭证、播放 HMAC 是两套密钥，勿混用。

## 6. 编码：Hex、Base64 不是加密

二进制（密钥、HMAC 输出、密文）要进 JSON / URL / 日志时，先编码：

| 编码 | 特点 | 常见用途 |
| --- | --- | --- |
| **Hex** | 体积约 ×2，字符集 `0-9a-f` | 本项目 `sign` |
| **Base64** | 体积约 ×4/3 | JWT、HTTP Header |
| **Base64URL** | 换掉 `+` `/`，去 `=` | URL 安全场景 |

注意：

- 编码**可逆**，不提供任何保密
- 比较签名前确认双方同一编码、同一大小写
- URL 里优先 hex 或 Base64URL，避免 `+` `/` 被转义搞砸

本项目 `hex(byte[])`：每字节拆高/低 4 位 → `Character.forDigit(..., 16)` → 小写十六进制。

## 7. 随机数、密钥与配置

### 7.1 随机数

- 安全相关一律用 **CSPRNG**：Java 里 `SecureRandom`，不要用 `Random` / `Math.random()`
- 用途：密钥、token、nonce、fileId 等不可猜测 ID

### 7.2 密钥存放

- 环境变量 / 密钥管理服务（KMS、Vault），**不要**写进代码仓库
- 不同用途拆分：`VOD_PLAY_SECRET` ≠ MinIO secret ≠ DB 密码
- 轮换：预留双密钥窗口（新旧都能验，只签发新）再下线旧密钥

### 7.3 密码存储（登录场景）

用户密码：

```text
正确：Argon2 / bcrypt / scrypt（慢 + 盐）
错误：明文、可逆加密当「哈希」、单次 MD5/SHA
```

与 HMAC 密钥不是一类问题。

## 8. 传输层：多数时候先上 TLS

应用层再怎么 HMAC / AES，若 HTTP 明文传输，token、cookie、签名 URL 仍可能被窃听或中间人篡改。

实践建议：

1. 对外接口 **HTTPS**
2. 内网也逐渐 TLS 化（视威胁模型）
3. 应用层签名解决「URL 被转发滥用 / 过期控制」；TLS 解决「链路上被偷被改」

签名 URL 的 `e`（过期时间）是在 TLS 之外再加的一层**时效与防篡改**控制。

## 9. 选型速查

| 场景 | 建议 |
| --- | --- |
| 播放 / CDN 限时 URL | HMAC-SHA256 + 过期时间（本项目） |
| Webhook 验真 | HMAC，原始 body 参与计算 |
| 密码登录存储 | Argon2id / bcrypt |
| 字段级保密落库 | AES-GCM，密钥进 KMS |
| 跨组织签发、公钥可分发 | JWT ES256 / RS256 等 |
| 浏览器访问 API | HTTPS；会话用成熟框架 |
| 仅防文件损坏（非对抗） | SHA-256 校验和 |

## 10. Java 速查（与本仓库相关）

```java
// HMAC-SHA256 → 原始字节
Mac mac = Mac.getInstance("HmacSHA256");
mac.init(new SecretKeySpec(secret.getBytes(StandardCharsets.UTF_8), "HmacSHA256"));
byte[] tag = mac.doFinal(payload.getBytes(StandardCharsets.UTF_8));

// 恒等比较（防时序攻击）
MessageDigest.isEqual(expectedBytes, actualBytes);
```

库选型经验：

- 标准库 `javax.crypto` / `java.security` 够用多数 HMAC / AES-GCM
- 复杂协议优先成熟库，避免自研 TLS、自研 JWT 解析
- 测试用固定 secret + 固定输入对照 **golden value**（见 `PlaySignServiceTest`）

## 11. 安全清单（上线前）

- [ ] secret 仅环境注入，未进 Git / 镜像层明文
- [ ] 签名字段拼接规则有文档，且签发 / 验签共用同一实现
- [ ] 比较 MAC / 签名使用恒等比较
- [ ] 有过期时间或 nonce，防重放（按业务）
- [ ] 日志不打印 secret、完整签名 URL（可打 fileId / 是否验签成功）
- [ ] 对外强制 HTTPS
- [ ] 单元测试覆盖：正确签名、篡改、过期、空签名
