# 04：课表鉴权与业务边界 — 实现思路

> 对应边界：不要把课表鉴权做进 Lite VOD；课权仍在业务服务（如天机学堂）。  
> 现网 Lite VOD 只认 `fileId` + 播放签名，不认 `userId` / `sectionId` / 是否已购课。

## 1. 两种鉴权分别管什么

| 层级 | 问题 | 谁负责 | 现网 |
| --- | --- | --- | --- |
| **课权 / 业务鉴权** | 这个用户能不能看这节课？ | 业务服务（tj-media / 学习中心） | 天机侧 |
| **媒资 / 点播鉴权** | 这个 URL 有没有被篡改、过期？ | Lite VOD 网关 | HMAC `e/sign` |

```text
学员点击播放
  → 业务服务：登录态 + 课表 / 订单 → 通过
  → 业务服务：向 Lite VOD 申请 playUrl（可带 exper）
  → 播放器：带签名拉 HLS
  → Lite VOD 网关：只验签名与 path，不查课表
```

## 2. 为什么不要做进 Lite VOD

1. **职责**：VOD 是存储与点播能力；课表、班级、订单属于业务域，变化频繁  
2. **复用**：同一套 Lite VOD 可服务多个业务（培训、内部培训、Demo），不应绑死天机表结构  
3. **安全模型**：课权用会话 / JWT；媒资用短 TTL 签名 URL，拆开更清晰  
4. **对接成本**：若 VOD 内嵌课表，每个客户都要在 VOD 建用户体系，变成「第二个业务中台」

实现文档也写明：业务服务负责课表鉴权、小节绑定；Lite VOD 不负责课表。

## 3. 正确拼法（推荐）

### 3.1 播放

```text
Client → 业务 API「申请播放」
         ├─ 校验登录、课权、试看策略
         └─ 调用 Lite VOD GET /vod/signature/play
Client ← playUrl
Client → Lite VOD /hls/...（仅签名）
```

### 3.2 试看

- 业务决定：无课权时是否允许试看、试看多少秒（`exper`）  
- Lite VOD 执行：L0/L1/L2 技术手段（二期 L2 见 [03-试看L2](../03-试看L2.md)）  
- **策略在业务，能力在 VOD**

### 3.3 上传 / 删除

- 管理端权限（谁能上传、删媒资）在业务或网关 BFF  
- Lite VOD 管理接口首期可无用户态（Demo）；生产应加服务间鉴权（mTLS / 内网 / gateway token），**仍不是课表**

## 4. 若「错误地」把课权做进 VOD，会变成什么

```text
Lite VOD 要存：用户、课程、章节、购买关系
  → 与天机双写或沦为唯一业务库
  → 播放验签前查库：网关变慢、与 HLS 高 QPS 模型不符
  → 多租户时 schema 爆炸
```

这是产品级重构，不是二期小需求。

## 5. 服务间鉴权（可做，但不是课表）

生产可增强、且仍属 VOD 边界内的：

| 项 | 说明 |
| --- | --- |
| 管理 API | 仅内网；或 `Authorization: Bearer` 服务账号 |
| 回调 Webhook | 签名校验或 IP 允许列表 |
| 播放签发 | 仅业务服务可调，不对浏览器直接暴露无限签发 |

这些是「谁能调 VOD」，不是「谁买了哪门课」。

## 6. 对接天机时的检查清单

- [ ] 播放前课权在天机校验  
- [ ] Lite VOD 无 user/course 表依赖  
- [ ] `exper` 由天机传入，VOD 不解释业务含义  
- [ ] 文档与面试口径统一：**能力在 VOD，课权在业务**

## 7. 一句话边界

> Lite VOD 保证「有合法播放签名才能拉到流」；业务服务保证「只有有课权的人才能拿到合法签名」。两道闸，不要合成一道塞进 VOD。
