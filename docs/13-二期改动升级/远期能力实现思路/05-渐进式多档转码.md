# 05：渐进式多档转码（先低清可播，再异步补高清）

> 目标：缩短「上传完成 → 可播放」时间：先出低码率档并允许播放，再异步补齐高码率档，更新 `master.m3u8`。  
> 定位：在 [多码率 ABR](../02-多码率ABR.md) 之上的体验优化；**不纳入当前二期「一次出齐多档」的默认实现**，单独立项。  
> 上级：[远期能力实现思路 · 阅读说明](./00-阅读说明.md)

## 1. 为什么有必要

当前 ABR（方案 B）是一次 FFmpeg 同时出 360 / 480 / 720，再写 master、标 `FINISHED`。

| 问题 | 表现 |
| --- | --- |
| 首播等待长 | 用户必须等最高档也压完才能播 |
| 算力前端加载 | 三路编码抢同一批 CPU，墙钟接近「最慢档」 |
| 体验与生产差距 | 云点播常见「先可播、后补档」 |

渐进式多档把「可播」和「档位齐全」拆开：

```text
可播时刻 ≈ 低清档转完 + 上传 + 写库
档位齐全 ≈ 后续高清任务完成 + 刷新 master
```

## 2. 目标体验

1. commit 后仍先 `PROCESSING`
2. **仅 360p（或 480p）就绪**时即可签发播放（`media_url` 已指向可用清单）
3. 播放器先播低清；高清档就绪后，刷新 master，弱网仍可降档、好网可升档
4. 全部计划档位成功（或明确放弃补档）后，任务终态与 Webhook 再通知「处理完成 / 档位齐全」

建议对外两层语义（名称可再定）：

| 语义 | 含义 | 用户侧 |
| --- | --- | --- |
| 可播（Playable） | 至少一档 HLS 可用 | 「申请播放」可用 |
| 档位齐全（LadderReady） | 配置的 ABR 档都已出齐 | 清晰度列表完整；可选二次 Webhook |

## 3. 与现网 ABR 的关系

| | 现网「一次出齐」 | 渐进式 |
| --- | --- | --- |
| FFmpeg | 一次 `filter_complex` 多路 | 先单档（或极少档），再补档 |
| `FINISHED` 时机 | 全部档上传完 | 可改为「可播即 FINISHED」，或增加中间状态 |
| `master.m3u8` | 一次性写全 | **可多次覆盖**，档位递增 |
| 实现复杂度 | 低 | 中：任务拆分、清单刷新、失败策略 |

渐进式**不否定** ABR；它改变的是「多档何时出现」，不是「要不要 master」。

## 4. 推荐产物与状态机

### 4.1 对象键（与现 ABR 兼容）

```text
hls/{fileId}/master.m3u8          # 可变，随档位增加而重写
hls/{fileId}/360p/index.m3u8
hls/{fileId}/360p/segment_*.ts
hls/{fileId}/480p/...             # 异步后出现
hls/{fileId}/720p/...
cover/{fileId}.jpg                # 建议与首档一并产出
```

首版 master 可以只有一档：

```text
#EXTM3U
#EXT-X-STREAM-INF:BANDWIDTH=800000,RESOLUTION=640x360
360p/index.m3u8
```

补档后覆盖为三档（与 [02-多码率ABR](../02-多码率ABR.md) 示例一致）。

### 4.2 任务拆分（建议）

用 **两类 MQ 消息**（或同一队列不同 `taskType`）：

```text
1) procedure.fast   下载原片 → 截封面 → 转 360p（veryfast）→ 上传 → 写 master(仅360)
                    → media 标可播（见下）→ 投递 procedure.ladder
2) procedure.ladder 转 480p / 720p（可串行或有限并行）→ 上传各档
                    → 重写 master（含已有全部档）→ 标档位齐全 → Webhook
```

原则：

- 快路径用更快 preset（如 `veryfast`），优先 TTFP（Time To First Play）
- 补档可用 `medium`，画质优先
- 补档失败**不要**把已可播媒资打成 `FAILED`（除非产品要求「必须齐全」）

### 4.3 媒资状态怎么改

两条路，二选一（立项时定）：

**方案 S1（改动小）**

- `FINISHED` = 可播（至少一档）
- 另增字段：`ladder_status` = `PENDING | RUNNING | READY | PARTIAL_FAILED`
- 播放只看 `FINISHED`；演示页「查状态」可展示 ladder

**方案 S2（语义更清晰）**

- 新增 `PLAYABLE`（可播但档未齐）与保留 `FINISHED`（档齐）
- 签发：`PLAYABLE` 与 `FINISHED` 都允许
- 兼容成本高：前端、天机对接、现有枚举都要改

**Lite VOD 建议先 S1**，少动播放主路径。

## 5. master 刷新与播放兼容

### 5.1 上传顺序（每次写 master 都遵守）

```text
先传齐「本批新增」的 ts + 子清单
再覆盖上传 master.m3u8
```

与现网「先 ts 后 m3u8」一致，避免播放器拉到新 master 却缺切片。

### 5.2 播放器侧

- hls.js 对点播 master 默认不会高频重拉；补档后用户**刷新播放**或重新「申请播放」才能看到新档，一般可接受
- 若要求「播着也能升出新档」：需缩短 master 的 `Cache-Control`，并让播放器定时 `loadSource` / 重载 levels（实现复杂，首版可不做）

### 5.3 签发与验签

现网已按 `media.media_url` 签 master 或 index，渐进式下：

- 可播起 `media_url` 就固定为 `hls/{fileId}/master.m3u8`
- 验签仍绑该 path；子路径共用签名
- **无需**因补档重新签发（除非换了清单文件名）

## 6. Worker 实现要点

### 6.1 快路径（示意）

```bash
ffmpeg -y -i source.mp4 \
  -vf "scale=-2:360" \
  -c:v libx264 -preset veryfast -b:v 600k -maxrate 600k -bufsize 1200k \
  -c:a aac -b:a 96k \
  -g 250 -sc_threshold 0 -force_key_frames "expr:gte(t,n_forced*6)" \
  -hls_time 6 -hls_list_size 0 \
  -hls_segment_filename "360p/segment_%03d.ts" \
  -f hls 360p/index.m3u8
```

再手写仅含 360p 的 `master.m3u8`，上传后更新 DB。

### 6.2 补档路径

- 每档单独 FFmpeg（实现简单、失败可单档重试），或二次 `filter_complex` 出剩余档
- **关键帧对齐**：补档命令与快路径使用相同的 `hls_time` / `force_key_frames`，否则 ABR 切档易花屏
- 原片仍从 MinIO `raw/{fileId}/source.mp4` 下载（或本地缓存未删时复用，注意磁盘）

### 6.3 幂等

- `ladder` 消息重复投递：已存在的 `720p/` 可跳过或覆盖；master 按「当前桶内已有档位」重建
- `media_task` 建议区分 `FAST` / `LADDER` 两行，或 `attempt` + `task_type` 唯一约束防双跑

## 7. API / 前端

| 点 | 建议 |
| --- | --- |
| 查询媒资 | 返回 `ladderStatus`、已就绪档位列表（可选） |
| 演示页 | `FINISHED` 即可播；文案区分「可播 / 高清处理中 / 档位齐全」 |
| Webhook | 可播发一次；档齐再发一次（`eventType` 区分），避免业务只认终态时丢「已可播」 |

## 8. 失败与降级策略

| 场景 | 建议 |
| --- | --- |
| 快路径失败 | 整任务失败，与现网一致，可重试 |
| 补档某一档失败 | `ladder_status=PARTIAL_FAILED`，保留已可播档；可重投该档 |
| 补档全部失败 | 仍可播低清；告警人工或定时重试 |
| 产品要求「必须 720」 | 快路径只作预览，对外可播仍等 ladder；TTFP 收益变小，一般不推荐点播主站 |

## 9. 配置草案

```yaml
vod:
  abr:
    enabled: true
    progressive-enabled: false   # 开关；false 时保持「一次出齐」
    fast-variant: 360p           # 首档
    ladder-variants: [480p, 720p]
    fast-preset: veryfast
    ladder-preset: medium
```

## 10. 验收建议

- [ ] 快路径结束后即可 `GET /vod/signature/play` 播通（仅低清）
- [ ] 桶内先有 `360p/` + 单档 master，后有 `480p/` `720p/`，master 条目增多
- [ ] 补档失败不把已可播媒资打成 `FAILED`
- [ ] 关闭 `progressive-enabled` 后行为退回「一次出齐」
- [ ] 删除媒资 `removePrefix(hls/{fileId}/)` 仍一次清掉

## 11. 工作量与风险（粗估）

| 项 | 说明 |
| --- | --- |
| 工期 | 约 3～5 天（含状态字段、双任务、演示页、测试） |
| 风险 | master 缓存导致客户端看不到新档；补档与快路径 GOP 不对齐 |
| 收益 | 演示机 / 弱 CPU 上 TTFP 明显下降；更接近云点播叙事 |

## 12. 立项结论（建议）

- **值得做**：私有化演示、长视频、单机 Worker 场景收益大  
- **可延后**：若二期只追求「master 能 ABR」，继续一次出齐即可  
- **不要和**「一次出齐 ABR」混在同一 PR：先稳定多档结构，再拆渐进任务
